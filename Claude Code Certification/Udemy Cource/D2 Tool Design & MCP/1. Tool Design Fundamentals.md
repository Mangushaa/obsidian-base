
# How claude select tools

- Tool Description - natural language text telling claude what a tool does and when to use it. Example - get_weather returns the current local temperature
- Routing - how claude matches request to the best-fitting tool from description
- Misrouting - when a vague description makes claude call the wrong tool

#### The description is the decision
- Tool names are hints, not rules - the description carries the weight
- Claude performs semantic matching between requests and descriptions
- A strong description narrows the candidate set to one obvious choice

**NOTE:** A weak or missing description makes every tool equally likely to be chosen

#### Strong vs Weak Descriptions

- Strng description - specifies waht the tool does, when to call it, what inputs it expects, and what it returns. Claude can confidently select it with minimal ambuguity
- Weak description -  gives only a name or vague phrases like "handles data". 

#### How selection actually works

- It assigns implicit relevance weights based on semantic fit to request
- Higher-confidence matches win over lower-confidence candidates
- No single keyword triggers selection - the full description context matters

## Routing outcomes
- Correct Call - right tool selected on the first attempt. Tkhe description was precise and unambiguous.
- Misroute - wrong tool called. Two descriptions read as too similar to tell apart.
- No call - no tool matched at all.
- Fallback - claude asks the user to clarify rather then guessing between unclear option

## Description Failure Modes

- Vague Intent - says what a tool is but not when to use it. Claude can't separate t from similar alternatives
- Missing scope - omits what tool does not handle. Overlapping tool create selection ambiguity.
- No output signal - doesn't say what the tool returns.


# Writing tool description that route correctly

- What it does - a one or two sentence purpose statement describing that tool's function without ambiguity
- When to use it - the conditions under which this tool should be selected
- When not to use - boundary conditions that scope the tool; what it doesn't handle is as valuable as what it does.

#### Include input format into description

- Reqeuired params
- Specify input format: JSON, array, enum, etc.

#### Include output format
-  State output format
- Not if output needs further processing or is ready to use directly
- Signal about error format, handl

## Reducing selection ambiguity

- Consolidate - group related operatoins into one tool with an action parameter instead of many overlapping tools
- Namespace names - prefix names by servuce, like github_list_prs, so selection stays clear as the library grows
- Exclude explicitlly - state what a tool doesn't handle.

## Testing tool selection reliability
- Try varied phrasing of the same underlying intent
- Rry requests that could match serveral tools - check which wins
- Try edge cases: requests the tiil should not handle

#### Testing patterns
- Positive test - send request that tool should handle
- Negative test - send request that tool should **NOT** handle
- Disambiguation test - send request mathing 2 tool, config correct tool wins

# Designing tool input schemas

- Tool schema - the JSON schema on a tool definition that defines: accepted parameters, their types and constraints 
- Input parameter - a named parameter in the schema
- Schema validation - the check that confirms claudes generated arguments match the declared schema before the call runs

#### Naming parameters
- use specific named 'customer_id' not 'id'
- use snake_case and avoid abbreviations the model might misread
- use description which help claude to understand what is param used for, it's format and constraints.

## Tool result schema

- tool_use_id - id that match request to response
- context - the result text or error msg when failed
- is_error - flag if response is error

#### Error response fields

- error_code - stable, machine-readable string. Never changes between releases of deploys
- message - a human readable explanation. Save to surface directly in a chat reply
- context - key-value pairs identyfyind exactly which input or resource failed.
- suggested_action - retry, escalate, or ask_user. Tells claude what to do next.

# Controlling Tool Seclection

**NOTE:** By default model decides whether to call a tool.  The 'tool_choice' parameter lets you steer thta decision.

- auto - the model decides whether to call any tool. This is default.
- any - the model has to call one of your tools, but it picks which one
- tool - you name a specific tool and the model always calls that one
- none - blocks model from calling tool at all

## When you force a tool call

- Setting 'any' or 'tool' prefills the reply so a tool call is gurunteed

#### Things to watch

- Caching cost - changing tool_choice invalidates cached message blocks. Tool definition and the system prompt stay cached.
- Extending thinking - with extended thinking only 'auto' and 'none' are supported, 'any' and 'tool' return an error 
- Prefilled reply - 'any' and 'tool' prefill the assistant turn, so no explanation appears before the call.

# Tool Search for Large Catalogs

#### How tool search works

- You add a 'tool search' tool to your tools list and it does the finding
- Deferred tools (marked wtih defered flag) stay out of the active context
- When model needs some tool it execute 'tool_search' tool that will find needed tool from catalog, and then put it's schema into active context.

#### Ways to search catalog

- Regex variant - the model writes regex patterns to match against you tool fields. 
- BM25 Variant - the model searched with plain natural-language queries instead of patterns.
- What it scans - both variant looks across names, description, arg names and descriptions.
