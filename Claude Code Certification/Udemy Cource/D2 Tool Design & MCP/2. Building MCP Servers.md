# What MCP and Why it exists

#### The integration problem MCP solves
- Each tool had it's own API contract and auth schema
- Developers rewrote glue code for every new capability
- Swapping tools meant rewriting application logic 

#### The MCP client-server model
- The server hosts and expose capabilities
- The client - app or agenst host - connect and discover capabilities
- One client can connect to multiple servers at once

#### MCP is Model-Agnostic

- Open Standart - Any AI model or runtime can implement it 
- Uniform Interface - servers don't know which model consumes them; clients non't know who build the server.
- Composable - mix and match MCP servers from diffirent vendors without integration rework.

#### How caude connects to an MCP server

1. Claude connects and nagotiates capabilities in an initialize handshake
2. It then calls list methods to enumerate tools, resourecs, and prompts
3. Those available capabilities populate it's context
4. The model then reasons over those capabilities like any other concepts

#### Key MCP concepts
- Transport Layer - the communication channel between MCP client and server. Standart I/O for local processes, or Streamable HTTP for remote servers.
- Capability Discovery - the process by which an MCP client queries a server to learn which tools, resources, and prompts are available before any request are made
- Capability Negotiation - 

#### MCP in Production AI Systems

- Capability teams ship independent MCP servers without coordination overhead
- Application teams consumes them without knowing implementation internals
- Upgrades happen server-side without breaking clients downstream


# MCP Primitives
 
- Tools - a callable function model inclides to perform action or retrieve computed resultls. Model-controlled
- Resources - A URI addrasable data object the application inject into context. Application=-Controlled
- Prompts - A reusable parameterized template users select to pre-populate an inteaction. User-Controlled

#### Tools
- Defined with JSON schema dedscribong inputs and outputs
- The model decides what and whether to invoke a tool
- Examples: run a query, send a message, call a callculation

#### Resources 

App injects them

- Identified by URI - the server registers what's available
- The application decides which resources to include, not the model
- Exampels - a config file, a database record, a policy document

#### Prompts 

User selects Them

- Stored and versioned on the MCP server
- Parameterized - the user fills in variables at selection time
- The user explicitly applies a prompt, not the model or app


# Building MCP Server

- MCP Server - a process exposing tools, resources and prompts to clients over a transport. Handles capability registration, request routing, and response formatting
- MCP Inspector - the official MCP debugging tool that lets developers explore registered tools, send test requests, and inspect response without full client.

#### Common Init Mistakes
- Registration after run() - tools added after run() is called are never send to client during capability negotiation


# Defining and exposing tools via MCP

#### Text Result vs Structured Results

- Texe Result - return a plain string when the model needs to read and present information. Simple, human-readable, and reasy to compose
- Structured Result - return a JSON when downstrem code needs to parse the results. Best for multi-field records and lists.

#### Common tool patterns

- Database Query - accepts filter parameters, run a query, and return rows as structured list.
- API Wrapper - accept request parameters, call an external HTTP API, and return the parsed response.
- File System Access - accept a path and operation type: read or write; and return content.

# Defining and Exposing resources

URI, Name - mandatory
MIME type - optional

#### Static vs Dynamic resource

- Static Resource - content that does not change between requests. Config Files, reference docs, fixed lookup.
- Dynamic resources - content generated or fetched at request time. Database query results, live api responses.

#### Resource Templated for dyamic URIs

e.g file://{path}

- Templates are discovered separatly through resources/tempaltes/list
- The client fills the parametr, then calls recources/read on concrete URI.

#### Common resource types

- File Resources - plain text or binary files. Use the file:// scheme with a content type of text/plain or binary.
- Database records - query resukts returned as JSON. Use db:// scheme and declare type application/json
- Config snapshots - key-value settings from config-store. Use config:// and return structured text the model reads.

#### Resource subscription and notification

- A client subscribes to a resource URI after initial retrieval
- The server sends a notification when resources content changes
- The client re-fetch the updated context when notification arrive

#### Exposing resource from a Server

- Declare the resource in the server's resource list at startup
- Implement a read handler that returns content for a given URI
- Optionally implement a subscribe handler for change notification.


# MCP Prompt templates: Design and Use

Basically it's predefined paramatrized prompt that can be fetched and used by user. So user fetch prompt passing parameters and gets fully usable prompt that will be passed to model.


#### Use cases for Server-Side Prompt Templates

- Multi-step analysts - structured prompts that enforce a repeateable methodology
- Compliance workflows - aapproved instructions sets that can't be rewritten ad hoc
- Onboarding tasks - guided prompts that walk users through unfamiliar processes

#### Prompt Versioning Strategies

- Version in Name - append a version number to the prompt name. Simple but each version is a new entry
- Version in argument - pass version as a runtime argument and resolver the right body server-side.
- Deprectation Flag - mark old templates deprecated in the response so clients can warn users.

#### How clients access prompt templates
- Call prompts/list to retrieve all available tempaltes and their argument schemas
- Collect argument values from the user through host UI
- Call prompts/get with name and filled argument values
- Inject the rendered prompt into the conversation as the opening context


#### Designing Arguments for Reusability
- Keep required arguments minimal - each one adds friction for users
- Provide sensible defaults for optional arguments to lowe r the entry barrier
- Use types arguments so clients can validate input before calling prompts


# Implementing MCP Client and Connecting to Server

- MCP Client - Software, like Claude Desktop or Cursor, that connects to servers and routes model requests
- STDIO Transport - spawns the server as a child process, communicating over standart I/O. For local, single-user use
- Streamable Http - Runs the server as an HTTP service tiwth streaming supprt: for remote multi-user production deployments.

#### Keeping catalog fresh

- A server declares a listChangedCapability during init
- It then sends a list_changed notification when it's catalog changes
- The client re-runs list_tools() or list_resources() to refresh it's cache
