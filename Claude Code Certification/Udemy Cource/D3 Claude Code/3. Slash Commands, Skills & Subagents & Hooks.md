
# Creating Custom Slash Commands

- Slash Command - a user-defined shortcut that maps a /keyword to a reusable prompt stored in a markdown file under ./claude/commands/.
- Merged into Skills - now skills approach is more recommended then commands.
- $ARGUMENTS - a placeholder in a command file that gets replaced with whatever text follows the command keyword when invoked.

Same as CLAUDE.md. there are project level commands and user level
-  Project - .claude/commands/
- User - ~/.claude/commands/

File naming becomes the command 
- deploy-review.md - /deploy-review
- run-tests.md - /run-tests

- Include a role statement "You are reviewing a pull request"
- State the task and the expected output format
- Add constrains like language, tone, or scope

# What Skills Are and When to Build Them

**NOTE:** Skills can be executed same way as Slash Commands but skill name is folder name, when command name if file name.

**NOTE:** Skills seat in /.claude/skills/{skill-name}/SKILL.md
#### Skill build decision framework 

- Frequency - not sense to write skill for one time job 
- Complexity - is it multi-step enough that a reusable template adds value
- Reusabilty - make sense to create skill when it will be reused across users, sessions.

#### Skill file blocks

- Frontmatter - metainfo about skill in yaml format (name, description, ...), it's optional
- Markdown body - instructions

If frontmatter is omitted claude can pickup skill by name.


Frontmatter:

- name and description
- when-to-use
- allowed and disallowed tools
- model, effort, context (fork - force to use subagent)
- agent and hooks ???
- paths - restrict skill to certain file paths 
- argument-hin - signal the arguments the skill expects when a user chooses to invoke it directly. (If claude runs skill automatically args will be replaced with empty strings, so it's better to add default values for such placeholders)

# Hook Lifecycle Events

- Hook - a command you register to run automatically when a specific lifecycle event fires in Claude Code.
- Lifecycle event - a named moment, like a tool call or session start, where hooks get a change to run
- Blocking hook - a hook that can stop the action from happening, signaled by existing with code 2.

#### Lifecycle groups

- Once per session - fires once at session start/end
- Oner per turn - fires around each prompt submit and stop
- Every tool call - wraps every pre-tool-use and post-tool-use call


#### Session-level-events

- SessionStart
- SessionEnd
- **Both are observe-only, so they cannot block anything**
- Set up context on entry or clean things up on the way out.

#### Turn-Level events

- UserPromptSubmit - fires when you send a prompt, before Claude reads it.
- Stop - fires when Claude finished responding
- **Both can block, which makes them useful gates** ??? What it point for blocking on stop?
- Prompt-submit can reject or reshape a prompt and stop can force more work

#### PreToolUse & PostToolUse

- PreToolUse - fires before tool runs. It can block the call.
- PostToolUse - fires after tool succceds. Cannot block, can be used to react, log, check output

#### Moment Specific Events

- PreCompact - fires before context compaction and can block it. So can be used to protect what gets summarized away
- Notification - fires when Claude Code sends a notification, and it only observes, so it's for alerting you ??
- Permission events - fire arount permission prompts, where a permission request can be denied by a blocking hook.  ??

#### Hook Output

- Exit zero - success. Claude Code reads any structured output the hook printed and continues normally
- Exit two - a blocking signal. For hooks that can block, exit two stops the action and feeds message back 
- Other codes - threated as non-blocking error for most events, so the action stoll proceeds anyway



# Plan mode

- Plan mode - read only thinking phase, permission mode
- Shift + Tab - enter plan mode
- /plan - enter plan mode for one prompt, after rollback to prev mode


#### Scope and Context in Planning

- Iterative refinement - producing a draft, reviewing it with a human or agent, and revising until quality critiria are met. Plans improve through iteration
- Plan-Mode Pairing - cmbinning plan mode with subagents for investigation or hooks for validation to improve reliability on complex changes
- Codebase Exploration - in plan mode Claude reads files and explores the codebase to build the plan. Approving the plan is what moves the session into making edits


# Iterating in a Plan: Approve, Edit, Redo

#### The most common plan-mode failure

- An unexpected file state prompts Claude to adapt silently
- Claude adds steps not in the plan without surfacing them
- You end up reviewing code that doesn't match what you approved

Counter this by asking Claude to stop and surface any divergence rather that work around it.
