
# JSON Mode and Schema-Constrained Output

#### Structured output terms

- Structured Outputs - feature that forces Claude's text reponse to match a JSON schema you supply. Set through the output config format field on the request.
- Declares spec definninig field name, types and allowed values.
- Constraint decoding - model pick up only token that fits into schema.
-
#### Output config format shape

```
{
  "model": "claude-3-5-sonnet-20241022",
  "max_tokens": 1024,
  "messages": [
    {
      "role": "user",
      "content": "Extract the user profile for Jane Doe, age 30."
    }
  ],
  "output_format": {
    "type": "json_schema",
    "schema": {
      "type": "object",
      "properties": {
        "name": { "type": "string" },
        "age": { "type": "integer" },
        "skills": {
          "type": "array",
          "items": { "type": "string" }
        }
      },
      "required": ["name", "age"],
      "additionalProperties": false
    }
  }
}
```

**NOTE:** claude can not follow schema only in 2 case:
- A refusal
- max token cutoff

#### Grammar Compile and Cache

The schema compiles into a grammar, and that step has real timing behavior

- The firest request on a new schema pays a one-time compile latancy
- The compiled grammar is cached for twenty-four hours from last use.
- Changing schema structure or the tool set invalidates that cache
- Renaming a field or description alone does not force a recompile

# Tool Definitions for Extraction ???

- Extraction tool - capture data, not run a side effect. It's input schema describes the fields the model fills from source text
- Strict tool use - setting strict to true on a tool definition it guaranteed the tool call arguments conform to the declared input schema
- Input schema - the typed field definitions on a tool. It names each field, sets it's type and marks which fields required


#### Tools as an extraction Target

- Define a tool whose input schema is the shape you want
- Ask the model to call it over the source text
- It returns a structured argument object, not free text
- Your code reads fields directly, no parsing to fail


### Two ways to Constrain

- Structured Outputs - Constraint the model's text response to JSON schema. Reach for it when the whole reply should be structured data, like a direct extraction of classification result
- Strict tool use - constrains the arguments of a tool call to the tool's input schema. Reach for it when the model is calling functions and each call has to be well formed.

# Validation Loops and Hallucination Control

#### Reliability Concepts

- Validation Loop - a pattern where extracted output is validated after generation. On failure, the error is fed back into a follow-up prompt for correction
- Hallucination Prevention - technique like grounding, citation instructions, and schema constraints that redice plausible but incorrect output
- Grounding - injecting source material or retrieved context so the model extract from evidence rather that from memory, reducing confabulation. 

#### What to validate after extraction

- Schema compliance
- Business rules
- Semantic correctness
- Cross-field consistency

### Re-prompt design on failure

-  Include the Error - paste the specific error into the re-prompt. Vague 'try again' instruction give the model nothing to fix
- Reference the source - re-incldue the relevant source text so the model re-extract form evidence rather the correcting from memory
- Constrain the correction - instruct the model to fix only the failing fields instead of regenerating the entire output, which can add new errors.

#### Hellucination prevention techniques

- Grounding - inject retrieved sources text so the model extracts, not generates
- Cititation instructions - ask the model to cite the sourec for each field
- Schema constraints - enum, req/opt
- Temperature - lower values reduce variance but do not fix grounding gaps

### Grounding and Context Injection

- Inject the specific source document or retrieved passage into the prompt
- Instruct the model to extract only from provided text, not general knowledge
- Ask for explicit source citations to make grounding auditable
- For multi-document extraction, label each source so citations are traceable

#### When Validation Loops Are Worth the Cost

- High-Stakes Output
- Big Scale and Maximum Automation 


# Validation Gates and Retry Strategy


- Retry cap - add cap to prevent infinite loop
- Temperature backoff - add a small increase on each retry to inject variance
- Change wording on retry to break same failure path

#### Validation Concepts

- Reviewer Pattern - a second model call that critiques the output against a checklist
- Escalation Path - What to do when retries run out: error, human review, or safe default
- Semantic Drift - when retries pass format checks but drift from the intended meaning

#### When to escalate instead of retry

- Same semantic error appears across multiple attempts
- Escalate when format passes but content meaning is consistently wrong
- Escalate when the failure points to a prompt design flaw not a model hiccup


# Multi-Pass Review: One Pass Enough

#### Review Concepts

- Reviewer Pattern - a second model call that critiques the first call's output against an explicit checklist before the result is returned
- Self-Review - a reviewer pass run by the same model that produced the output. Cheaper, but more prose to confirmation bias.
- Cross-Review - a reviewer pass run by a different, often stronger model for a genuanly independent critique.

#### Designing Effective Reviewer Prompts

- Use an explicit checklist, not open-ended 'find issues' instructions
- Specify what a passing result looks like, not just what failures looks like
- Ask fir a structured critique: which check failed, and why with suggested correction


#### Reviewer Checklist Categories

- Completeness
- Accuracy
- Tone and Format

#### When Multi-Pass is Worh the Cost

- High-stakes
- Regulated omains
- Long-form content  where a missing secion is hard to catch on a casual read


# Building a Prompt Evaluation Workflow

#### The core eval Loop

Dataset -> Run -> Grade -> Compare

- Dataset - curated inputs with knows expected outputs 
- Run - send each input through the prompt and collect responses
- Grade - score each response against the expected output or criteria
- Compare - measure the new version against the current baseline

#### Key Eval Metrics

- Pass Rate - % of eval cases where output metts grading criteria.
- Regression rate - share of previously passing cases that now fall after a change.
- Latency - avarage reponse time per eval case. Relevan when a prompt change could slow model output.
- Cost Per Eval - total token spend divided by case count. Tracks whether the prompt stays within operational budget.

#### When to run

- Before each deploy
- After dataset change
- By schedule


# Test Datasets Generation and Model-Based Grading

- Code-Based Grading - Programmatic assertions, regex, or schema validators that decide whether an output meets correctness criteria. Fast and deterministic.
- Model-Based Grading - a separate model scores the output against critiria or reference answers. Handles subjective outputs that code cannot check


#### Ways to Generate Test Datasets

- Handcrafted - manually written cases targeting know failure modes.
- Synthetic - generated by a model from a seed set of topics or patterns
- Production-sampled - real inputs drawn from logs, reviewed and labeled
- Blend sources - mature eval suited combine all three

#### What makes a good test dataset

- Typical cases
- Edge cases
- Adversarial inputs - cases designed to trigger failures or expose weak spots
- Volume - enough cases that the pass rate is statistically meaningful

#### Code-Based Grading Tecniques

- Exact Match 
- Regex
- Schema validation
- Unit tests

#### Model Based Grading Design

- The grader receives the input, the output, and scoping criteria
- The rubric defines what a passing response looks like across dimensions
- The grader returns a score, a pass or fail label
- The grading prompt needs version control and testing like any prompt

Risks: 
-  Grader Bias - the grader may favor outputs stylistically similar to it's own defaults, inflating scores for certain formats or tones
- Untested Grading Prompts - the grading prompt is a prompt too. If it's not evaluated and versioned, grader quality can drift silently
- Scores as Ground Truts - model based score are estimates.  Without calibration against humans, the overstate measurement precision


#### Calibrating Model-Based Grading

- Sample a representative subset of eval cases and have humans label each one.
- Run the same cases through the model grader and compare results
- Calculate agreement rate: the fractoin where grader and human agree
- Adjust the grading rubric where systematic disagreements appear
