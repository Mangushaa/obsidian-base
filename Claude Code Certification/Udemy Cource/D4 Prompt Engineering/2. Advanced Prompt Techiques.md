
# Why Examples Work in Prompting

#### Few-Shot prompting Terms

- Few-Shot Prompting - two or more examples before the task 
- Zero-Shot Prompting - a task with no example at all 
- One-Shot Prompting - exactltly one example provided

Examples is send alongside user original prompt and model reference it as example.

Messages[0], [1] is example. [2] - user prompt. Model reference [0],[1] as ideal response.

```
{
  "system": "You are a professional corporate communicator. Your job is to take angry user input and rewrite it into polite, constructive corporate language.",
  "messages": [
    {
      "role": "user",
      "content": "Tell marketing they are moving too slow on the ad campaign."
    },
    {
      "role": "assistant",
      "content": "Hi Marketing Team, checking in on the timeline for the ad campaign. Let me know if you need any blockers cleared so we can keep things moving."
    },
    {
      "role": "user",
      "content": "Tell Sarah that if she schedules another meeting at 5 PM on a Friday I am going to quit."
    }
  ]
}
```

#### What examples communicate

- Format - the exact structure the output should follow 
- Tone - formal, conversational, terse, or detailed
- Reasoning pattern: how to approach the task step by step
- Scope - what to include and what to leave out

**NOTE:** Examples do all this simultaneously, while prose adresses one dimension at a time.


#### How examples anchor patterns

- Model not just read example as prose
- The model identifies structural patterns across all examples provided
- It extract implicit rules: length, phrasing style, output sequence
- Those tules apply when the new input differs from the examples
- Examples tend to transfer format and tone more reliably then prose
- Pattern matching from examples produces more consistent output then instructions alone

#### Prose Instruction vs Examples

- Prose Instructions - describe the desired output in natural language. The model must interpret what the description means and translate it to output. Interpretation introduces varience, especially for novel formats
- Concrete examples - show the desired output directly. The model can mirror the demonstrated pattern. Format, tone and structure tend to transfer implicitly and more reliably

#### Shot count tradeoffs

- Zero-Shot - no examples. Instuction is simple, and output format not important
- One-Shot - works when task in single pattern.
- Three-Shot - covers most format and tone variation. The most broadly useful for structured output
- Five-Shot or More - useful when example it really different across different input types .

# Designing High-Quality Few-Shot Examples

#### Example diversity

- Cover different input lengths, topics and phrasing styles
- Include at least one edge case that tests the boundry pattern
- Avoid clustering all examples around the most common case
- Diversity ensures the model generalizes rather then overfitting to one type

#### Static vs Dynamic Few-Shot

- Static - best when all input set is predictable and same across turns
- Dynamic - examples are selected at runtime by similarity. Needs a retrieval step but improves output quality

#### Avoiding Example Contamination 

- Stylistically skewed examples reproduce unusual phrasing across all outputs
- Topic-biased examples cause the model to assume all inputs share that logic
- Overly long example outputs train the model towad excessive length
- Artifacts unique to one example get coped verbatim into other responses


#### Dynamic Few-Shot Selection

Example Pool -> embed for similarity -> retrieve top-k matches - inject into prompt


#### Ordering Effects in Few-Shot Prompts

- Recency Bias - models give more weight to later examples. The final example has the strongest influence on output format and tone.
- Put Best Last - place your most representative, highest-quality example last. It anchors output more strongly than earlier examples.
- Vary in testing - if output quality varies unexpectedly, try reorder

#### Testing Whether Exampels Help or Hurt

- Run the prompt with examples, then without, and compare output quality
- If zero-shot matches few-shot quality, the examples adding noicse
- If output reproduces example artifacts, contamination has occured
- Test on diverse inputs, not just the canonical case the examples resemble


# Chain-of-Thought - Prompting for Visible Reasoning

CoT - Chain of thought
Scaffold - каркас

- Chain of throught prompting - show reasoning before the answer
- Zero-Shot CoT - trigger reasoning with no examples
- Structured CoT - give a labeled reasoning scafflod 


#### Zero-Shot CoT: Think Step by Step

- Append 'Think step by step' to trigger visible reasoning
- Variants 'Walk me through your reasoning' or 'Explain before answering'
- Effective for arithmetic, logic puzzles, and multi-step planning tasks
- Omitting the trigger phrase and expecting reasoning to appear on its own is a common error.

#### Structured CoT: Providing a Scaffold

- A structured scaffold guides the model through a fixed reasoning pattern
- A scaffolds gives consistent reasoning across related tasks
- Free-form reasoning fits tasks whose steps keep changing.

# Extended thinking 

- Extended thinking - an API feature for internal thinking blocks before visible response. Enabled via the thinking parameter, not prompt text
- Thinking Blocks - internal reasoning segments produced during extended thinking. Streamed as distinct event types before the final response; not part of the output text.
- Adaptive Mode + Effort - Claude decides hot much to reason, guided by an effort level (high is default; xhigh and max go deeper). Cost is capped by max tokens.

#### Controlling Reasoning Depts

- Claude decides how much to reason, not a fixed budget
- You ssteer depth with an effor level: low, medium, high default, xhigh, max
- Max tokens caps thinking plus output together
- A fixed token budget is legacy, for older models
- Match effort to complexity balance depth against cost

#### Thinking Blocks in Practice

- Separate from Output - stremed as distinct event types before the final response; not part of the answer text
- Count against context - thinking blocks consume context tokens even through they don't appear in the final answer
- Not prompt text
- Surfaced as Events - clients handle streaming event types explicitly to read or display thinking block content

# Steering Model Output


#### Prefilling on the flagships

- What prefilling was - ending JSON request the messages array with a partial assistant turn so the model continues from a chosen opening token
	```
	{
  "model": "claude-3-5-sonnet-20241022",
  "messages": [
    {
      "role": "user",
      "content": "Extract the hero's name and age from this text: 'Neo is 28'."
    },
    {
      "role": "assistant", // Assistant
      "content": "{\n  \"name\":"
    }
  ]
}
	```
- Where it stopped - the 4.5 generation and later reject it with a 400. Pre-4.6 models like Haiku 4.5 still allow it.
- What to do instead - reach for structured outputs, strict tool use, or system prompt steering each achives control by supported means. 

#### Steering Concepts 

- Output steering - guiding the model toward a target tone, structure, or scope using supported insructions rather that injecting a partial response turn
- System-prompt steering - setting persistent behavior in the system prompt so tone and format hold across every turn in the conversation
- Format control - directing the shape of a response through explicit instructions, examples, and schema-backed features that guarantee structure.

#### Supported replacements 

When prefilling would have shaped output, three supported features nnow cover the same needs

- Structured outputs - guarantee schema-valid JSON in the text response
- Strict tool use guarantees valud arguments on every tool call
- System-prompt steering - shapes tone, scope, and format across turns

#### Format Control Without Prefilling

- State the target format plainly in the instructions
- Show one ot two examples of the exact shape you want
- Name required fields and their value types explicitly
- For guaranteed JSON, use structured output instead 
- Instructions plus examples handle most needs; schema features handle the strict one

#### When to use which feature

- Need guaranteed JSON - use structured output it conforms to your schema normally; refusals and max tokens cutoffs still need handling
- Need valid tool arguments - use strict tool use. It guarantees each tool call's arguments match the input schema exactly
- Need tone, scope, style - use sytem prompt steering.

#### Clarification Turn Design

# Conversation State, Context Accumulation, Turn Management

- Context accumulation - the growth of conversation history as turns are added. Usfeul context enables coherence; excees context creates noise and window pressure
- Context Drift - the gradual shift in topic, tone, or task framing across long conversations. Behavior can diverge from original intent without obvious failure.
- Nouse Buildup - The accumulation of repeated, contradictory, or obsolete content in history. Noise dilutes the signal from current instructions.

**NOTE:** Periodic re-anchoring keeps drinft from compounding 

#### Context drift correction and repair patters

- Be explicit - name what was wrong rather than restating the whole prompt
- Correct one issue at a time to avoid compounding confusin
- Reaffirm the correct context before asking for a redo
- Verify the repair produced the right change before moving forward


#### Reset vs Continuation Decision

- Continue when - history is coherent, recent turns stay on course, and the model already has the context it needs to proceed
- Reset when - Noise has built up, drift has taken thinkgs off course, or task changes made prior conext a liability
- Partial reset -  Start a new thread but carry forwards only essential context: key decisions, constraints, and relevant outputs. Leave the noise behind
