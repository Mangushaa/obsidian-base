
# How the Token Window Works - Tokens, Limits and Tradeoffs

- Context Window - everything a model can see in one inference call: prompt, history, documents, and the model's output
- Token - the atomic unit a model processes, roughly 4 chars or 3/4 of an english word.
- Context Window Limit - the hard maximum token count for one request, combining all input and output. Exceeding fails.

#### Input vs Output Tokens

- Input Tokens - everything passed to the model: system prompt, history, documents, tool definitions, and the user message. Usually the larger share in RAG and agent pipelines
- Output Tokens - the text the model generates. Output counts against the limit and usually costs more per token then input. Long reasoning consumes output budget quickly

#### How Different Content Types Tokanize

- PLain prose - roughly one token per four chars
- Code - tokanizes afficiently because keywords are common
- JSON and XML - structure punctuation adds overhead
- Non-English text - many languages use more tokens per word

#### Choosing a Claude Model Tier

- Claude Haiku - the smaller-window, low-latency tier at 200K tokens. Fits fast, lightweight single-turn summarization and classification.
- Claude Sonnet - 1M token window at lower cost. Balances capability and price for multi-document retrieval and agentic pipelines
- Claude Opus - 1M token window with top capabillity. Chosen for the hardest reasoning not a bigger window then Sonnet.

#### What happens when window fills

- Input too large - a 400 error rejecets the request before any generation.
- Mid-generation overflow - output stops with model context_window_exceeded
- Hard truncation - dropping oldest messages loses critical context.
- Handling code has to treat an upfront rejection and a mid-stream stop as separate cases.

#### Context Budget and Context Rot

- Context Budget - a deliberate token allocation across prompt, history, retrieved chunks, and output headroom, enforced in code.
- Context Rot - antrophic's term for attention diluting as tokens grow, so recall and instruction following degrade.
- List in the Middle - a position-based framing where content in the middle of a long context gets less attention then the start or end

#### Working Within Context Limits 

Well-designed systems work within context limits rather than against them

- Summarize history - compress long conversations instead of carrying them verbatim
- Retrieve selectively - chunk and pull only the most relevant documents
- Cap output - set explicit output token limits to preserve input headroom
- Track usage - watch token per request to catch runaway growth early

# Context Window Economics - Cost, Speed & Quality

- Context windows economics - the cost-benefit tradeoff of how much context to include, balancing quality against price and latency
- Token Pricing - the per-token rate for input and output. Output costs more then inpu; higher tiers charge more
- Latancy - time from request to response. Larger context raise time-to-first-token

#### The latency cost of long contexts

- Streaming helps it hides prceived latency, but total time still scales
- KV cache - reduces latency for repeated stable prefixes

 
#### Cost Levers in Context Design

- System prompt - try to reduce as much without quality affect
- History policy - summarize older turns to cap history token spend
- Retrieval Precision - Loosely relevant documents waste tokens. High-precision retrieval lowers chunk count and cost

#### Why More Context is Not Always Better

- Noisy retrievals - dilute the signal of the truly relevant chunks
- Contradictions - conflicting passages cause inconsistent responses
- Long contexts - can reduce instruction following precision

#### Quality Mechanisms

- Attntion Dilution - reduced focus on relevant content when irrelevant or redundant tokens dominate the context
- Retrieval Precision - the fraction of retrieved chunks that are genuinely relevant. High precision lowers noise.
- Prompt caching - an api feature that reuses a stable prefix's computation to cut latency and input cost. Cached token billed on a reduced rate.


#### Prompt Caching as an Economics Tool

- Mark cacheable - flag a system prompt or document prefix 
- Compute once - the first request builds the cache; later ones uses it
- Cheaper tokens - cached tokens are billed at a much lower rate
- Faster start - time to first token drops as prefix work is skipped


# Why Summaries Lose Facts

- Persistent Fact Block - a structured, addressable prompt region holding extracted facts that persists through 
- Fact Extraction - a step that pulls structured facts out of turns into a separate block

#### Facts that Get Lost

- Identifiers: user IDs, ticket numbers, version string
- Numeric limits - token budgets, rate limits, cost thresholds
- Named entities - people, tools, datasets, and services
- Decisions - choices make earlier that constrain later steps

#### Symptoms of Fact Loss

- Constraint amnesia - a rule stated early in the session is silently ignored several turns later
- Entity Confusion - the model substitutes a plausible name or value for the one the user actually specified
- Decision Drift - a commited choice gets reopened as if still undecided , turns after agreement

#### How Loss Compounds Across Turns

- First pass - minor details dropped from early turns
- Second pass - a summary of a summary loses more
- Third pass - only the broadest narrative survives

#### Update strategies

- Append-only block - a persistent block that grows by adding new facts and never overrites prior entries
- Replace-on-Conflict - a new fact value overrites an older value for the same key when the two disagree
- Extract-first pattern - run fact extraction before summarization so no facts are consumed in the compression pass.


#### Extract First, Summarize Second

- Step 1 - pull structured facts from the new turn
- Step 2 - write extracted facts into the persistent block
- Step 3 - summarize the turn for rolling history


Facts are captured before the summarizer can discard them

- Fact aging - removing facts not referenced in recent turns to keep block size bounded. 

#### Extraction Prompt Design

- Specify categories - identifiers, numerics, decision, named entities
- Request structured output - JSON with types fields per category
- Handle gaps - instruct the model to output null for missing categories

####  Injecting the Block into Requests ???

Where toy place the block affects how reliably the model uses it.
Options:
- Top of user turn - visible but competes with the actual question 
- Separate system block - authoritative and clearly scoped (BEST)
- Inline before the query - high salience but slightly verbose

#### Size Management Strategies

- Cap the block - set a hard token limit and refuse new facts once reached
- Age Out Stale Facts - remove facts not cited in the last N turns
- Merge redundant entries - consolidate facts about one entity under a single key.
- Priority Tiers - mark facts permanent or ephemeral only age out ephemeral ones.

#### Handling Fact Conflicts

Conflicts arise when the same fact appears with different values

- Detect - compare incoming facts to existing block entries
- Log both - record old and new values before overwriting
- Escalate - ask the user when conflict is significant

#### Validation and Downstream Checks

- Downstream Validation - confirm the block matches the latest input and no facts wew silently dropped
- Schema enforcement - validate that extracted facts match expected types and ranges before writing 
- Round-Trop Check - re-extract facts from the block output and compare to the source turn to catch errors 

#### The most common failure mode 

- Unused block - it exists in the prompt but no instruction references it
- Wrong source - the model answers from general knowledge instead
- Expensive no-op - the block costs tokents but changes nothing

# The Memory Tool for Persistence

Compaction keeps a session going but loses detail. 

- Memory tool - a tool the model uses to read and write files under a memory path, so facts persist across separate conversations.
- Client-side tool - a tool where the model request an action and your application actually performs it against storage you control
- In-context memory - anything the model knows only because it sits in the current transcript. It vanishes when the context is cleared.

# The Tool-Output Bloat Problem

- Tool-Output Trimming - reducing a tool's response to only the fields the agent needs before it enters context.
- Signal-To-Noise Ratio - the proportion of relevan content to filler in context. a primary friver of output quality
- Context Window Pressure - When accumulated tokens crowd out relevant content and the model attends to noise 


- Reference Indirection - store the full response externally and pass the agent an identifier to fetch it on demand.
- Trim Audit Log - a record of fields the trim layer discarded, useful when a downstream agent needs a missing one

# Trim Strategies: Filter, Summarize, Reference

- Field-Level Filtering - a deterministic trim that keeps a fixed list of fields and drops everything else before context entry.
- Model-Driven Summarization - route the raw output through a small model that distills it to a compact, task-relevant summary
- Reference Indirection - store the full response externally and pass the agent an identifier to fetch on demand

#### Stable Schema vs Unstable Schema

- Stable Schema -> Filter - when structure is predictable, declare the fields once and the wrapper run deterministically.
- Unstable schema -> summarize - when structure varies across versions, a fixed field list breaks. A small summarizer adapts
