
**Task Decomposition** - process of splitting high level goal into smaller subtask that can be assigned to agents, tools, or workflow steps.

**Handoff Point** - the boundere between subtask where otput of one step becomes input for other. **Requires an expilit schema!**

**Orchestrator** - controlong agents that decomposes agoals, assign subtasks, manages execution order, and synthesizes result.


## What makes a good subtask

- Single Responsibility - each subtask does one thing
- Defined Inputs - the subtask lnows exactly what context and data it receives
- Clean Output - Output is structured and explisit, so orchestrator can route results without parsing raw text.
- Bounded Scope - scope is small enough to retry on failure without re-running whole workflow 

## Decomposition Patterns

**Hierarchical** - Goals split into subgoals and so on on different levels forming the tree, where leafs are tasks, and levels above are subgoals with total goal in the root. Orchestrator delegates down, results flow back.

**Sequential Execution** - tasks performed in order, where each step may depend on the prev step output.

**Parallel Execution** - independent subtask run concurrently, reducing total runtime. Required synchronization point to collect result.

## Decomposition Antipatterns

**Over Decomposition** - to many steps, coordination costs exceeds execution costs.

**Under decomposition** - tasks to large to retry or delegate

**False parallelism** - threating dependent steps as independens causing some tasks do not have enough input.

# Parallel Execution 

## Why Parallel Agent Execution Increases Cost

LLM API pricing is based on **total tokens**, not execution time. While parallel execution cuts latency, it increases overall token volume—and thus total cost—due to: 
- Context Duplication Every parallel branch must be initialized with the full system prompt and background context, multiplying your input token usage. 
- Synthesis Tax An additional aggregator LLM call is required to reconcile, de-duplicate, and merge independent outputs from parallel workers.
- Wasted Speculative Work Unlike sequential pipelines, you cannot "early-exit." If a parallel dependency fails or succeeds early, you still pay for the concurrent tasks that were already triggered
- Verbosity & Bloat Independent agents tend to generate full, verbose payloads rather than concise state deltas, as they lack visibility into the work of other agents.

Fan-Out - point where work in branching into parallel tasks.

Fan-in - point where parallel tasks are synced into one result.

**Fan-in responsibilities**
- Collect results - gathe output from each task that completed succesfully
- Handle Failures - decides what to do when one or more tasks failed
- Order results - reassembles outputs in the right order when seq metters.
- Merge and continue - aggregate collected results and pass to next step.

## Partial failure handling

- Fail the pipeline - if any branch failed, faild full pipeline.
- Proceed with partial results - continue with what succeded, flag what failed
- Retry failed branches - retry failed branches rather that all fan-out.

## Result merging strategies 

- Voting - multiple branches answer same question, majority result wins
- Concatenation - outputs from independent branches are joined into one output list.
- Structured Aggregation - each branch contributes a named fields to shared object. useful when each branch compute diffirent field for same object.


# Adaptive Planning - Updating the plan Mid-Execution 

**Static Planning** - a fixed seq of steps authored before execution. The agent follow script without deviation

**Dynamic Planning** - the plan is generated and revisited at a runtime based on new info or unexpected state

**Replanning** - revising the current plain in response to new info, failed steps, unexpected output, change environment, etc.

# Handling Ambiguity and Incomplete Specification

**Ambiguous goal** - a task specification that does not fully define the expected outcome, leaving multiple interpretations open to the agent.

**Clarify-First strategy** - pausing execution to request more information from human before proceeding

**Assume-and-Proceed** - making a reasonable assumption and continue without human interrupt. Usually used when action is low-stakes, reversible, or time-sensitive.


When to clarify upfront:
- Irreversible actions (deletions, commiting transactions, etc)
- High cost operations - extensive APIs or long batch results
- Scope uncertainty - the agent doesn't know what's in or out
