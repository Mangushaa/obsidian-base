
Orchestration Concepts:
- Orchestrator - controlling agent that decomposes a high-level goal into subtasks, assign them to subagents and aggregate results. 
- Task decomposition - breaking complex goal into smaller subtasks that can be delegated to individual agents, or tools for execution
- Result Aggregation - collecting result from agents, validating them and synthesizing then into single response for initial goal


## What the orchestrations retains

Orchestrator holds:
- Master plan
- Execution state
- Error handling logic
- Aggregation rules
- Final synthesis
- All subtasks results

Subagent holds:
- What orhestrator passed to subagent. 
	- instructions, context, tools to use


# Subagent Design

Subagent - a separate agent instance spawned by parent orchestrator to handle delegated subtask within it's own bounded context and tool permisions. 

Context isolation - subagent operate in their own context window. No information passes form orchestrator to subagent unless it's directly handed over.

Authority Boundary - set of actoins that subagent can use, and nothing else.


## Context isolation 

Subagent is spawned with fully empty context. All context then subagent needs to perform a task should be passed by orchestrator.

**Why context isolation metters**

- Less Bloat - subagent do not carry irrelevant context
- Less Leakage - limits information leaking between tasks and agents
- Lower costs - minimal context per subagent

**Antipatterns in subagent design**

- Overly broad scope - the subagent is asked to do too much at once
- Unpowered context - orchestrator pass to less info to complete a task
- Unclear success criteria - the subagent don't know when it's done


# Subagent topology

- Hub-and-Spoke - a central orchestrator routes all tasks and communication to preiphiral agents. Spokes do not communicate
- Pipeline - agents arranged in linear sequance. Each agent process input from previous agent and passes output to next.
- Peer-to-Peer - opposite to hub&spoke agents communicates directly wout central coordinator.


## Hub&Spoke

Pros
- Centralized State Management
- Simple failure handling owned by one node
- A clear audit trail for every decision
- Easy to enforce consistent delegation policies from one place
Cons
- A single point of failure at the hub
- The hub's capacity caps total system throughput
- Hu context grows with each active spole, risking token bloat
- More spokes amplify both bottlenecks and risk

## Pipeline Topology

Pros:
- Every agent has a narrow, single responsibility within sequance
- Stages are modular and easy to swap, test, or replcae independently
- Each stage produces a clean artifact the next stage uses as full input
Cons:
- Total latency - equals sum of all stage, no concurency
- A failed mid-stage agent blocks every downstream stage
- Cascade failue risk grows with depth

Ideal when transformations are strictly ordered and each output is testable.

## Peer to Peer

Pros:
- Low latancy, agents talk directly, skipping central coordinator
- Resilient - no single agent failure that down all system

Cons:
- Hard to audit - no central log or state 
- Harder to predict, test, and control

# Designing Agent to Agent schemas

**Schema concepts**:

- Handoff message - a structured payload with task, context, output format, and constraint the receiver needs to complete a task

- Schema versioning - version tags on handoff formats so receiver parse messages event as the schema evolves.


**Handoffs antipatterns:**

- Missing Context - receiver lacks the information neede to act correctly
- Inconsistant Format - no agreed structure, receiver parse raw task and assume what needs to be done
- Implisit assumption - sender assumes the receiver knows thinks it does not

**Core Schema Components:**

- task
- context
- output format
- constraints

# Handoff Protocols and Agent Continuity

**Handoff protocol concepts**

- Handoff verification - configrming the receiver is prepare before sender hands off the task
- Error propogation - how subagent failures surface back to controller so it can respons
- Silent Failure - a handoff that look successful but loses critical info, with no error signal.

## Handoff Verification Steps

1. Sender Send handoff
2. Receiver Acknowledge receipt
3. Receiver confirm ready

## Designing error propogation

- Subagents return structured error payloads, not silent nulls
- Error payloads include failure type, context, and recovery hints
- Orchestrator need explicit error paths, not only happy paths

# State management

## Memory concepts

- In context state - what agent know right now, inside live context
- External memory - persistent stores outside the model (db)
- Semantic retrieval  - querying a vector index by meaning not by key to retrieve relevant chunks

# Session Continuity and failures

## Continuity concepts

- Session resumption - resuming a task from a checkpoint after interruption, without repeating completed steps
- Checkpoint - a saved snapshot of task progress at a phase boundry to recover to after failure
- State versioning - tracking which environment version a checkpoint used to detect conflicts on resume
