
# Per-Field Confidence Scores

- Field level confidence - a score emitter per extracted field rather that for a whole record.
- Rauting Threshold - the cutoff above which a field is auto-accepted and below which it's sent to review
- Calibration - empirical alignment between  emmitted scores and real accuracy on real labeled set 


#### The Coarse-Confidence Problem

One score for the whole record conceals which individual fields are unreliable 

- Hidden weak spots - a record at 0.85 may hide a date field at 0.4.
- Wasted review - reviewers recheck high-confidence fields they could skip.
- Blind policy - decisions on the aggregate miss the fields that need help

#### Eliciting Per-Field Confidence

There's no native confidence field. The score is a verbalized self-report you prompt the model to produce.

- Ask the schema to hold a value key and a confidence key per field 
- The model estimates the score; it's not a raw internal probability
- A self-reported number means nothing until a held-out set calibrates it
- Prompt design elicts the score; calibration is what makes trustworthy


#### Reading the Score Output

- High Confidence - auto accepted
- Low confidence - Flagged and queued for a human reviewer to verify
- Borderline Score - near the threshold; policy may add a secondary check or a tighter per-field cutoff

#### Routing Policy

- Pre-field routing - routing decided independently for each field
- Pre-record routing - routing the whole record to review when any single filed falls below the threshold.


# Calibrating Confidence Scores


- Validation Set - a held-out, labeled dataset used to measure accuracy and calibrate confidence thrsholds
- Reliability Diagram - a plot of confidence versus empfirical accuracy that reveals over and under confidence
- Routing threshold - the confidence cutoff adjusted after calibration to reflect real accuracy, not raw output


#### Building a validation Set

- Representative - draw from full distribution of real documents
- Labeled - every field has a ground truth value you are measuring
- Held out - the set is never use to train or prompt the model (Why???)

#### Running the Calibration Check

Four steps turn a validation set into a calibration result

- Bucket by Score
- For each bucket measure accuracy based on labeled data
- Plot the Result
- Find the gaps

#### Reading a Reliability Diagram

The diagram maps what the model claims to what it actually delivers

- X-axis: model confidence from 0 to 1
- Y-axis: empirical accuracy (actual model accuracy for that bucket) from 0 to 1
- Diagonal a perfectly calibrated model traces it exactly
Gaps between the line and the diagonal reveal where the model misleads routing

#### Adjusting the Routing Threshold 

Set the threshold to the score that delivers the accuracy you policy requires.

- Pick the target - find the required accuracy level on the diagram 
- Read across - take the mathing confidence value on the x-axis
- Set it - use that confidence value as the routing threshold

#### Recalibrating After Changes

- New model - a version change shifts the confidence distribution
- New prompt - a revision can move scores on identical documents
- Rerun it - repeat the check on the same validation set after changes

# Stratified Sampling for Review

Stratified - розшарована, сегментована

- Stratified Sampling - selecting review items disproportionately from low-confidence, rare, or high-stakes outputs.
- Stakes Weighting - adjusting review routing by the downstream impact of an error, independent of the confidence
- Reviewer Burnout - when reviewers get too much correct output and miss real error when they finally appear. 

#### Why Random Sampling Falls Short

A model that is 95% accurate means 95% of random samples look fine.

- Rare failures - reviewers seldom see the 5% that matters
- Hidden patterns - errors stay invisible across category boundaries
- No extra scrutiny  - high stakes outputs get none by default

Random review gives a false sense of quality without catching what breaks


#### Random vs Stratified Review

- Random Sampling - easy to implement, with every output equally likely to be picked. Reviewers see mostly correct outputs, so errors are statistically rare in the review queue.
- Stratified Sampling - needs confidence scores and category labels, and oversamples failures and edge cases. Reviewers see concentrated signal and catch more real errors per hour.


#### Stratifying by Confidence score

- Set a floor - below 0.7 confidence triggers oversampling
- Still sample the rest - high-confidence outputs enter at a lower rate
- Tune the ratio - balance between reviewer capacity against error tolerance

#### Stratification Dimensions

- Confidence - oversample outputs below your confidence floor, regardless of category or impact
- Category balance - ensure rare output classes get reviewed proportionally, not drowned out by common ones
- Stakes - route high-impact outputs through review event when the model is confident.

#### Stratifying by Output Category

Category-based stratification protects against class imbalance in queue.

- Common drowns rare - frequent classes will fill the queue and hide critical ones
- Set quotas - per category sample limits guarantee coverage
- Rare carries risk - rare categiries often carry the most risk

#### Combining Strata Effectively

- Confidence x Category - select items that are both low-confidence and from underrepresented categories, concentraining signal
- Confidence x Stakes - high-stakes outputs get reviewed event at high confidence, in a separate lane from low-confidence pool.
- All three combined - full stratification uses confidence, category and stakes to maximaze error yield per hour.


# Routing Through a Review Queue

- Review Queue - a work surface where low-confidence outputs land for human inspection before downstream release
- Reviewer action set - approve, reject, or edit that close the HITL cycle
- Bypass Policy - A rules letting certain outputs skip the queue on confidence or urgency.
#### Queue Architecture Overview

The review queue sits between the model's output and its downstream consumer

- Low goes to queue - low confidence outputs are routed, not released
- High flows on - high confidence outputs continue downstream with no delay
- Held until acted - the queue holds items until a reviewer acts

#### What reviewers See in the Interface

A good interface presents everything needed for a fast, accurate decision.

- The input - the original request that generated the output
- Output and score - the model output and its confidence side by side
- A suggestion - a proposed correction from a secondary system if available

Reviewers should never leave the interface to find context for a decision


#### Closing the Loop With Training Data

Reviewer correction are the most valuable signal a model team can collect

- Approve - confirms: it validates the model's behaviour on the input type
- Edit labels - each correction is a labeled pair for fine-tuning
- Reject - flags: it marks an input class the model handles poorly

Feeding corrections back into training creates a continuous improvement cycle.

#### Latency Tradeoff and User Expirience

- Synchronous - the user is blocked until decision is made
- Asynchronous - a placeholder returns now and is fulfilled lated
- Or bypass - some cases tolerate delay, other need a bypass path.

#### When to Use the bypass Policy

- Emergency override - time critical cases where review delay causes more harm than the eror risk
- High-Confidence floor - output above a validated confidence ceiling skip review with logging.
- Reviewer Unavailable - a fallback when no reviewers are active and operation must keep moving

# Claim-to-Source Mappings - why every sentence needs a source

- Provenance Tracking - attaching a verifiable source pointer to every claim so reviewers can confirm where each fact come from.
- Claim-to-Source Mapping - an explicit structure linking each output claim to the source documents it derived from
- Inline Citation - a source pointer placed next to a specific claim, not at end of a paragraph.

#### Inline vs Paragraph Citations

- Inline - reference next to claim (sentence) each sentence source can be identified
- End Of Paraprah List - citations are in end of paragraph shows which sources formed paragraph, but separate sentance source can't be identified


#### Schema Design for Claim Mapping

Store each claim alongside the identifiers of every source that supports it.

```
{
  "claim": "Revenue grew 12% in Q3"
  "source_ids": ["doc_4", "chunk_19"]
  "confidence": 0.88
}
```

#### Why Provenance Tracking Matters

- Trust - stakeholders trust output they can spot-check against sources
- Auditability - auditors trace any fact to it's source without re-running the model
- Compliance - GDPR Articles 13-15 and the EU AI Act require showing where conclusions came from
- Error correction - a flagged claim traces to its source, so fixes stay local not full resynthasis

#### The Verification Workflow

A structured verification workflow lets reviewers sample claims and confirm them against sources without reading everything

- Select a random or risk-weighted sample of claims
- Follow each claim's source pointers to the cited documents
- Confirm the source tet supports the synthesized claim
- Sample size depends on error rate, tolerance, and confidence, not a fixed %


- Source Identifier - a unique, stable reference to a document, chunk, or passage used as evidence
- Fabricated Citation - when a model invents a source that does not fit or does not exists.
- Sampling Audit - a review checking a subset of claims against their source pointers.

# Conflict Annotation - Surfacing Disagreements in Synthesis

When sources disagree, surface the conflict instead of silently picking one


#### Core Conflict Concepts

- Conflict Annotation - showing in the output that sources disagreed on a fact, instead of silently selecting one
- Resolution strategy - an explicit rule for choosing among conflicting sources: prefer-newer, prefer-authoritative, or escalate
- Averaging Antipattern - blending or silently picking one or two conflicting claims, hiding the disagreement from the reader

#### Conflict Detection: Finding Desagreements

Detection identifies when two sources make incompatible claims about one fact

- Same topic - semantic similarity groups claims about one subject
- Contradiction - entailment checks test whethe claims conflict
- Flag the pair - high similarity but low agreement marks a conflict

Detection happens before synthesis not after, early flags drive better output. 

#### Recording Conflicts After Resolution

When a conflicts is resolved, preserve the trail once a winner is choosen

```
{
  "claim_a": "rate 5%"
  "claim_b": "rate 7%"
  "rule": "prefer_newer"
  "chosen": "claim_b"
}
```

A logged trail shows a decision was made, not that consensus existed


- Conflict Log - a persistenet record of each disagreement the strategy applied, and the outcome versus alternative
- Entailment check - a semantic test of whethe one pssage contradicts, supports, or is neutral to another
- Source Authority Ranking - a predefined hierarchy of trust levels used by the prefer-authoritative strategy

#### Surfacing conflicts for Readers

Annotation balances transparency with readability: overwhelming the reader defeats it

- High stakes - surface conflicts inline at the claim level
- Medium risk - use footnotes or expandable sections
- Full review - aggregate a conflict summary at the document end
- 
The goal is inform readers not exhaust them
