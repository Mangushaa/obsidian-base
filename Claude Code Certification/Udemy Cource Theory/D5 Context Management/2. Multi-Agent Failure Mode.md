
# When to Escalate - Trigger Design


- Hard triggers - explicit policy conditions in the system prompt; the agent always escalaets when they fire. Hitting a denylist, exceeding a cost threshold, or a sensitive action. No model judgment involved.
- Soft Triggers - model jusdgment conditions where the agent decides based on confidence or context. Ambiguous intent or low-confidence reasoning. These are tunable and calibrated over time.

#### Trigger categores

- Confidence below threshold
- Scope outside policy
- Repeated Retry Failure
- Ambiguous user intent

# The Handoff Payload - What the Next Actor Needs


- Handoff Payload - the bundle of context, history, and next step passed to the next actor
- Closing the Loop - reinjecting the resolverr's response into the original agent's context
- Escalation Routing - directing the payload to the right next actor: human, specialist, or supervisor

#### Core Payload Fields 

```
{
  "summary": "what happened before escalation"
  "tiggering_question": "the input that fired it"
  "attempted_actions": "the actions tried"
  "suggested+next_step": "the agent's best guess"
}
```

#### Routing the Escalation 

A structured payload can be routed to the right actor automatically. Routing logic lives in the orchestrator, not the escalating agent.

#### Common Handoff Failures

- Missing Context
- No suggested step
- Unroutable Format

#### Tracking Escalation as Data

- Log each handoff - trigger type, payload fields, routing destination
- Aggregate over time - find which triggers fire most often
- Refine from data - adjust thresholds, add allowlist entries, fix prompts

#### Closing the Loop

Escalation is a round trop; the resolver's response must be re-enter the agent's context

- Without closure - the agent resumes from it's pre-escalation state
- With closure - the agent gets the resolution and can continue
- Injection point: the context window the agent ascalated from


# Where to Catch the Error - Local or Up the Stack

- Local Recovery -  handling a transient or recoverable error inside the same agent that produced it.
- Coordinator Propogation - surfacing an error up to a parent agent or orchestrator so the higher-level plan can adapt
- Propogation Boundry - the interface where the architect decides which error surface to the coordinator

#### Silent Failure vs Thrashing

- Silent Corruption - whe subagent catches every exception and return success. The coordinator proceeds on a false premise, data degrades, and the defect surfaces only after cascading downstream damage.
- Coordinator Thrash - every minor retry or validation blip propagates. The coordinator spends most of its cycles on noise, retrying recoverable work it should never have seen.

#### Errors That Stay Load

- Transient retries - a rate-limit
- Recoverable validation - bad input the agent can sanitaze and reprocess
- Idempotent re-fetches - a stale cache miss the agent refreshes itself

#### Errors That Propagates Up

- Scope violations - subagent asked to act outside it's authorization
- Repeated failure - three attempts, no progress, no local path forward
- Policy denials - a guardrail or access control blocked the action

# Designing the Propagation Contract

#### Propagation Contract Vocabulary

- Error Envelope - a structured payload describing an error: type, severity, and recovery hint that travels up the stack
- Severity Level - a classification (warning, recoverable, or fatal) that decides whether the coordinator retries, falls back, or escalates
- Idempotency - the property that retrying an operation produces the same effect as running it once; required for safe propagation.

#### The Error Envelope Structure

```
{
	"error_type": "rate_limit",
	"severity": "recoverable",
	"context": {
		"agent_id": "A7", 
		"task": "fetch"
	}
	"recovery_hint": "retry with backoff"
	
	??? completed_steps
}
```

#### Coordinator Retry Options 

- Exponential Backoff
- Fallback Agent - route the task to an alternate subagent or model
- Partial Completion - keep finished steps and reroute the failed one
- Human Escalation - pause the chain and surface it to an operator


# The Silent Bug - When 'Nothing' is Ambiguous

- Tool Wrapper - a thin layer between the underlying tool and the agent that normalizes responses and reports status
- Status Enum - a field on every tool response naming the outcome so the agent can branch
- Ambiguous Nothing - an empty response that could mean an empty search or a failed access, the silents bug root


# Disambiguation Patterns and Tool-Wrapper Discipline

- Tool Wrapper - a thin layer between the raw tool and the agent that normalizes responses and enforces disambiguation.
- Status Enum - a structured field on every tool response naming the outcome so the agent branches instead of guessing
- Retry discipline - the wrapper's rule that access failures retry while confirmed empty results do not.

#### Wrapper Rule: Http Success vs Failure

- 200 with empty list - a valid, confirmed empty result
- 4xx or 5xx - an access failure regardless of body
- Timeout - an access failure event with no HTTP code at all.

#### The Status Enum: Outcome Classes

```
status = Enum(
	"success", # has results
	"empty_result", # mo match found
	"partial_result", # truncated
	"access_failure", # retry it
)
```
