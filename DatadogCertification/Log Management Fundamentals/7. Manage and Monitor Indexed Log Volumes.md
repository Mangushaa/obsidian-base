
#### Logging without Limits* pathway

After logs are ingested and processed, you can use tags and attributes from the logs to filter subsets of logs to create insights, store, or exclude (that is, discard) logs based on importance, and index logs that you need day to day. You can manage retention and daily quotas for the indexed logs to cut costs.

Below is the pathway for ingested logs in Datadog. (Note, not all these products/features will be enabled in every Datadog organization. Some of these features require activation and configuration.)

1. Logs are ingested by Datadog.
2. Logs are then [preprocessed](https://docs.datadoghq.com/logs/log_configuration/pipelines/?tab=source#preprocessing) (if they’re in the JSON format) and processed using [Pipelines](https://docs.datadoghq.com/logs/log_configuration/pipelines/?tab=source) and [Standard Attributes](https://docs.datadoghq.com/logs/log_configuration/attributes_naming_convention/#standard-attributes) to parse attributes, enrich logs details, and standardize attribute names across all logs.
3. Logs are scanned for sensitive data using [Sensitive Data Scanner](https://docs.datadoghq.com/sensitive_data_scanner). [Cloud SIEM detection rules](https://docs.datadoghq.com/security/cloud_siem/log_detection_rules?tab=threshold) are also implemented to detect threats and attacks.
4. [Error Tracking](https://docs.datadoghq.com/logs/error_tracking/) issues and [Anomaly Detection Watchdog insights](https://docs.datadoghq.com/logs/explorer/watchdog_insights/) are created from logs for troubleshooting and monitoring.
5. All ingested and processed logs can be searched in [Live Tail](https://docs.datadoghq.com/logs/explorer/live_tail/).
6. Before indexing or storing logs, any set of logs can be used to [Generate Metrics](https://docs.datadoghq.com/logs/log_configuration/logs_to_metrics/) for analytics and monitoring.
7. Logs needed on-hand daily for facet-based searches can be indexed using [Indexes](https://docs.datadoghq.com/logs/log_configuration/indexes). Logs needed ad-hoc occasionally can be assigned to [Flex Tier](https://docs.datadoghq.com/logs/log_configuration/flex_logs/). Unnecessary logs can be excluded using [Exclusion Filters](https://docs.datadoghq.com/logs/log_configuration/indexes#exclusion-filters).
8. Important logs that aren’t needed daily but need to be retained for incidents can be forwarded to [external archives (cloud storage)](https://docs.datadoghq.com/logs/log_configuration/archives/?tab=awss3) and [custom destinations](https://docs.datadoghq.com/logs/log_configuration/forwarding_custom_destinations/?tab=http) using Log Forwarding. These logs can be retrieved and indexed as needed by [Rehydrating from Archives](https://docs.datadoghq.com/logs/log_configuration/rehydrating). Rehydrated logs are not affected by exclusion filters in indexes.

# Indexes

Log Indexes provide fine-grained control over your Log Management budget. You can segment data into value groups for differing retention, quotas, usage monitoring, and billing.

Datadog recommends using multiple indexes if you require the following:

- Multiple retention periods
- Multiple daily quotas, for finer budget control

## Creating indexes

By default, each new account gets a single index (**main**) representing a monolithic set of all your logs. The filter in this index is `*`. All ingested logs are filtered into the **main** index.

You can create an index for any subset of ingested logs by using tags and attributes from log data to create the filter query. For each index, you can set the retention period, daily quota and reset time, and warning threshold

Index names must start with a letter and can only contain lowercase letters, numbers, or the ‘-’ character. Logs that are filtered into an index are assigned a tag based on the index name.

The index retention setting determines how long logs are stored and searchable in Datadog. By default, Datadog accounts come with the Standard Tier storage option for indexes. The Standard Tier is for indexing logs in the index so that they can be quickly queried for analytics and monitoring. You can set the retention to any value allowed in your account configuration. (By default, **15 days** is the only available retention period. You’ll need to contact Customer Success success@datadoghq.com to have other retention periods made available in your organization’s Datadog account.

## Ordering indexes

As you create indexes, be sure to move all indexes above the default main index and order the indexes as needed. The order of indexes in the Index list matters!

## Querying indexes

You can query across one or multiple indexes in Log Explorer using the `Index` facet.

# Exclusion Filters

By default, logs indexes have no exclusion filter. All logs matching the Index Filter are indexed. You can add exclusion filters to indexes to control which logs should be removed because not all logs are equally valuable.

Excluded logs are discarded from indexes but still flow through the [Live Tail](https://docs.datadoghq.com/logs/live_tail/) and can be used to [generate metrics](https://docs.datadoghq.com/logs/logs_to_metrics/) and be [archived](https://docs.datadoghq.com/logs/archives/).

Exclusion filters are defined by a query, a sampling rule, and an active/inactive toggle:

- The default query is `*`. All logs flowing into the index will be excluded. You’ll need to add a filter query to scope down the subset of logs that should be excluded.
- The default sampling rule is `Exclude 100% of all logs` matching the query. You can adjust the sampling rate between 0% to 100%. You can also decide if the sampling rate applies to all the filtered logs or to groupings of the logs defined by the unique values of any attribute.
- The default toggle position is active. Logs flowing into the index are discarded according to the exclusion filter configuration. When the toggle is set to inactive, the filter is ignored.


# Flex Logs vs Standard Indexing

[Archiving](https://docs.datadoghq.com/logs/log_configuration/archives/) is a better solution for logs that you need to keep long-term but query infrequently and without much urgency, for compliance and other purposes. If and when you do need to search archived logs, you can retrieve them using [Rehydrate from Archives](https://docs.datadoghq.com/logs/log_configuration/rehydrating).

You need a solution between indexing and archiving. Datadog offers this solution with [Flex Logs](https://docs.datadoghq.com/logs/log_configuration/flex_logs/). Standard Tier stores logs for real-time exploration, dashboards, and alerting, while Flex Tier stores logs for historical investigation using flexible query compute options. You can query subsets of logs occasionally as needed while not having to index all those logs all the time.

General recommendations for retention tier and storage option based on use case are listed below. Of course, your specific use cases may vary, so you should select the storage option for each of your use cases that best suits your needs.

- Use Standard Indexing for logs you tend to query frequently within a short time span (a few days to two months), such as application logs.
- Use Flex for logs you collect in high volumes, retain in the relatively long term (a few months to over one year), and sometimes urgently need to query, [such as security, transaction, and network logs](https://docs.datadoghq.com/logs/log_configuration/flex_logs/#potential-sources-for-sending-directly-to-the-flex-logs-indexing-tier).
- Use Archiving for logs you need to retain in the long term (years), but which you query infrequently and without much urgency, such as audit and configuration logs.

When a log matches an exclusion rule on a log index and is dropped from all indexes, **it is processed through the pipeline and then immediately discarded from Datadog's retention storage.**

### What Datadog STILL DOES with the Log

Before the log hits the index and gets dropped, Datadog's intake servers process it in memory. During this brief execution window, Datadog performs four specific actions:

1. **Routes to Archives (S3 / GCS / Azure Blob):** If you have an Archive configured, Datadog streams the raw log directly to your cloud storage bucket _before_ dropping it. You keep a long-term compliance copy for pennies without paying Datadog indexing fees.
    
2. **Generates Custom Metrics (Logs-to-Metrics):** Any metric rules you set up will parse the log text or JSON attributes in real time. For instance, if 10,000 HTTP 200 logs arrive, Datadog increments a metric counter `app.requests.count` by 10,000 and then drops the log lines.
    
3. **Streams to Live Tail:** The log remains visible in the real-time **Live Tail** stream in the Datadog UI for up to 1 hour (as long as a developer is actively watching the stream).
    
4. **Evaluates Sensitive Data Scanner / Pipelines:** Pipelines, grok parsers, and obfuscation rules still run on the log data as it enters intake.

# Considerations for Log Management Strategies

In general, consider these points while you’re determining whether you should index, flex, or archive logs from different sources:

- When you have incredibly high volumes (millions to billions) of the same log, you don’t need to keep every single one.
    - Apply sampling strategies (indexing a percentage of those logs, while excluding the rest) that ensure that you are indexing enough logs for an accurate representation of those logs.
- Not all logs are created equal.
    - For example, don’t store/index your debug logs unless you believe it’s necessary to do so.
- Some logs shouldn’t be “logs.”
    - For example, you can [generate metrics](https://docs.datadoghq.com/logs/log_configuration/logs_to_metrics/) for logs with low information density with low cardinality and sample them at a low percentage so that you can track their change over time and retain only some for investigations or audits while saving costs.
- “Don’t chase the tail”—apply the “80/20 rule” to your index optimizations and configurations
    - For example, don’t chase < 1% volumes. Focus indexing strategies on logs with higher volumes.

For more suggested indexing strategies, read the [Best Practices for Log Management guide](https://docs.datadoghq.com/logs/guide/best-practices-for-log-management/) and [Logging without Limits](https://docs.datadoghq.com/logs/guide/getting-started-lwl/) guide in the documentation.
