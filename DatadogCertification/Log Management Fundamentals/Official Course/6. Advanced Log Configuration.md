This course will cover the following topics:

- Gathering groups of log files using wildcards
- Condensing many lines of logs into single log events
- Filtering logs using inclusion or exclusion
- Applying processing rules at the local/service or global level

# Gathering Logs Across Files

Most services will write information to `stdout` and `stderr`, which are automatically collected by Datadog. However, many applications write logs across multiple files organized by time and directory.

The logs from your Postgres database are stored in `/var/log/postgresql/`. When a file reaches a certain size, the service rotates the logs into new files. The files will also rotate based on a schedule.

Datadog Integration configuration files provide an option for collecting logs from a file, but it might not be clear how to collect logs from multiple files. Collecting logs from a single file looks like the following configuration in an integration’s `conf.yaml` file:

```yaml
logs:
  - type: file
  - path: /var/log/postgresql/postgresql-15-main.log.1
  - service: postgres
```

To collect logs across files in a shared pattern or path, you can use the wildcard operator, `*`. You can use the following configuration to collect logs from all files in the Postgres log directory:

```yaml
logs:
  - type: file
  - path: /var/log/postgresql/postgresql-15-main.log*
    service: postgres
```

# Multiline Logs

**Multiline logs** occur when a single event consists of many log lines.
Datadog provides several options for grouping these related lines into one log event.

#### Pattern based configuration

The Datadog Agent allows you to define a pattern that identifies where each log event starts. The Agent will then group those lines into a single log. For example, you could specify that each log entry begins with a timestamp or a specific keyword. The Agent will consider everything from that pattern up to the next occurrence as part of the same log.

For example, a configuration for a Java application log might look like this:

```yaml
logs:
  - type: file
    path: /var/log/application.log
    service: my-service
    source: java
    log_processing_rules:
      - type: multi_line
        name: log_start
        pattern: "^\\d{4}-\\d{2}-\\d{2}"  # Example: Matches YYYY-MM-DD format
```


#### Auto detection for multiline logs

There is an `auto-detection` feature for logs which looks for incoming multiline logs. The feature can automatically identify some common patterns, such as timestamps, and group them together.

For more information on dealing with multiline logs, see the [advanced log configuration Datadog documentation](https://docs.datadoghq.com/agent/logs/advanced_log_collection/?tab=configurationfile#multiline-logs).

# Filtering Logs

You can use **Exclude Match** or **Include Match** rules to manage log inclusion and exclusion. These rules rely on **regular expressions** that match specific patterns in your logs.

#### Using exclude match

Use exclude match if you have a service that produces many logs, where only a few are not needed. In a Python service, you might exclude logs that contain the word `DEBUG`:

```yaml
logs:
  - type: file
  - path: /var/log/my-service.log
    service: my-service
    source: python
    log_processing_rules:
      - type: exclude_at_match
        name: exclude_debug_logs
        pattern: "DEBUG"
```

#### Using include match

For example, use include match if you only want to see logs that contain the word `ERROR`:

```yaml
logs:
  - type: file
  - path: /var/log/my-service.log
    service: my-service
    source: python
    log_processing_rules:
      - type: include_at_match
        name: include_error_logs
        pattern: "ERROR"
```

# Processing Rules

In Datadog, the decision isn’t always about which logs to include or exclude. It can be about ensuring logs appear in the right format. **Log processing rules** allow you to transform logs as they’re ingested.

Imagine a Python service with logs containing invalid characters, making logs hard to read.

To clean these up, you might define a local processing rule like the following:

```yaml
logs:
  - type: file
  - path: /var/log/python.log
  - service: storedog
  - source: python
  - log_processing_rules:
    - type: replace
      name: clean_garbled_characters
      source: python
      target: python
      pattern: "(\x9B|\x1B\[)[0-?]*[ -\/]*[@-~]"
      replacement: ""
```

This rule configures the Agent to replace any characters matching the pattern with an empty string.

## Global processing rules

**Global processing rules** apply to all logs collected by Datadog. You might want to replace all instances of a user email address in logs with a placeholder.

To do this, you might define a global processing rule in the Agent configuration file like the following:

```yaml
logs_config:
  processing_rules:
    - type: mask_sequences
      name: scrub_emails
      pattern: "(User email: )[^@]*@(.*)"
      replace_placeholder: "$1 masked_user@${2}"
```


For information on these subjects see the [Datadog documentation on advanced log configuration](https://docs.datadoghq.com/agent/logs/advanced_log_collection/?tab=configurationfile).
