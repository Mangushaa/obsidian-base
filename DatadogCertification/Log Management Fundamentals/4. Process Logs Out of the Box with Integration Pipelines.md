
With Datadog’s centralized log processing approach, you can define how each log should be processed into rich JSON content with standard attribute names.

# Centralized log processing in Datadog

1. Logs are ingested by Datadog.
2. [JSON-structured logs are preprocessed](https://docs.datadoghq.com/logs/log_configuration/pipelines/?tab=source#preprocessing) and the log details are parsed and listed as Event Attributes.
3. Logs are then filtered through pipelines for more processing. The Pipelines list in the image has six pipelines for logs from six different sources. Pipelines only appear in the list if you add or create them. The Filters column in the Pipelines list displays the query term for the filter. Logs will be filtered into the matching pipeline. For example, logs with the `source:nginx` tag will pass into the Nginx pipeline because it is the first pipeline in the list with the `source:nginx` filter. Logs that aren’t in the JSON-format and don’t match any pipeline filter will not be processed.
4. Any relevant Standard Attributes are also applied across all logs before they are passed to the next stage of log management.


In Datadog, ingested logs that aren’t in JSON format can be processed using [Pipelines](https://docs.datadoghq.com/logs/processing/pipelines/). A pipeline takes a filtered subset of ingested logs and applies a list of sequential [Processors](https://docs.datadoghq.com/logs/processing/processors/?tab=ui). Each processor completes a data-structuring action. A properly built pipeline results in structured, enriched logs.

To use an Integration Pipeline, you need to configure the log source with the relevant source tag (such as `source:nginx`) for that pipeline. When Datadog receives logs from that source for the first time, Datadog adds the matching pipeline automatically to the Pipelines list. Any new logs with that `source` tag will be filtered into the Integration Pipeline for processing.

# Unparsed logs

Parsed logs are central to using Datadog Log Management to its full capacity. As you use Log Management, you might see logs that don’t have a list of Event Attributes but instead have a message that says that no attributes have been extracted from the log message. These are unparsed logs.

Logs from a source may be unparsed for the following reasons:

- The source tag is incorrect.
- The logs from the sources are not configured correctly.
- An integration pipeline does not exist for that log source.

 Datadog assigns the `datadog.pipelines:false` tag to logs that are unparsed so that you can easily identify and track those logs.

# Creating and editing pipelines

When you create a new pipeline or clone an existing one, you set a filter so that a specific subset of logs passes through the pipeline. If no filter is specified, the pipeline is applied to all ingested logs. The pipeline filter uses the same query logic as [Logs Search](https://docs.datadoghq.com/logs/search_syntax/). 

# Nested pipelines

In addition to processors, you can add [nested pipelines](https://docs.datadoghq.com/logs/processing/pipelines/#nested-pipelines) to a pipeline. A nested pipeline filters a subset of logs from the parent pipeline and further enriches those logs.

# Order matters!

As you add Integration Pipelines, clone existing pipelines, and create custom pipelines, the order of pipelines in the Pipelines list matters. If you have multiple pipelines with the same filter, logs that match the filter will be processed by the pipeline highest up on the list. To ensure the correct pipeline is being used to process logs from a specific source, you can do one of the following:

- Adjust the order of pipelines in the list
- Disable pipelines you don’t need
- Add an additional tag to the filter query
